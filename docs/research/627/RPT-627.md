## 要旨

Kagi は Git 操作の実行前に結果を予測して提示する GUI である。本報告は「Git backend を
libgit2 に据え置くことが危険か、また遅いか」という問いを 7 つの実験パッケージで検証した
結果をまとめる。

当初の作業仮説は二つだった。(i) GitKraken や VS Code のように Git CLI を内包すれば
Git 本体と挙動が揃い安全である、(ii) libgit2 は遅い。**実測はいずれも支持しなかった。**

libgit2 の読み取り 4 経路は `.gitattributes` の filter を実行せず (F-01)、予測を libgit2
に置くことで repository config 由来のコード実行を構造的に回避できる。一方、hardening を
施した Git CLI 経路では repo-local の custom merge driver が実行された (F-02)。

速度面では、観測されていた遅さの主因が backend ではなく index stat cache の陳腐化で
あった (F-03)。修正後、50,000 file の repository を実機で開く時間は 4.25 秒から 0.09 秒に
なった。条件を揃えた比較では composite の `snapshot` は全規模で libgit2 が速く (F-06)、
単体 `status` のみ 20,000 file 付近で CLI が優位に転じる (F-05)。

結論として、既定 backend を libgit2 とし、CLI は利用者が明示選択する mode に限定し、
規模や環境による暗黙の自動切替は採らない (§7)。証拠は単一 host のものであり、
Linux / Windows は未検証である (§6.1)。

## 1. 序論

### 1.1 背景

Kagi の存在理由は、破壊的な操作の前に「何が起きるか」を提示することにある。したがって
**予測経路は敵対的な repository に対しても実行される**。この性質が backend 選定の制約を
通常の GUI とは異なるものにする。

### 1.2 問い

- **RQ1** libgit2 を予測経路に使い続けることは安全か。CLI に寄せた場合と比べてどうか。
- **RQ2** libgit2 は実際に遅いか。遅いとすればその原因は backend か。
- **RQ3** 両者の意味論は一致するか。混在させた場合に破綻する条件はあるか。

### 1.3 貢献

1. 予測経路における filter 実行の有無を、対照付きで実測した (§3.1)。
2. 観測されていた status 遅延の主因を特定し、修正して実機で検証した (§3.2)。
3. index 状態を正規化した条件下で backend 間の性能を比較した (§3.3)。
4. 上記から backend 選定の決定表を導いた (§7)。
5. **否定的結果を含む**測定手法上の落とし穴を記録した (§5)。

### 2.3 正規化手順 (重要)

§5.1 の交絡を除くため、性能測定はすべて次の手順に従う。

```

     （--no-optional-locks を付けない。付けると index が書かれず prime されない）
     → 2 warm-up を破棄 → 30 measured → backend の実行順を反転して再測定
```

計時中の index mtime 不変を確認し、read timing に write が混入しないことを保証した。
表中の `a / b` は `libgit2 → CLI / CLI → libgit2` の順序反転 series である。
**単一比率を採否の根拠にしない。**

## 3. 結果

### 3.1 安全性

**F-01 — libgit2 の読み取り経路は `.gitattributes` の filter を実行しない。**
確信度: 高 (対照あり、4 経路で再現)。

`statuses` / `diff_index_to_workdir` / index `add_path` / `checkout_tree` の 4 経路を測定し、
filter が実行されることを確認した bare `git add` を対照に置いた。4 経路はいずれも filter を
実行しなかった。

含意: 予測を libgit2 に置くと、repository config 由来のコード実行を**実装の注意深さでは
なく構造で**回避できる。

**F-02 — hardening 済みの Git CLI 経路では repo-local の custom merge driver が実行された。**
確信度: 高 (P2 E3、実測)。

`merge-tree --write-tree` を hardened `run_git` 経由で実行した際、repo-local の custom
merge driver が動作した。当時の `HARDENING_ARGS` は動的に命名される config key
(`merge.<n>.driver`、`filter.<n>.*`、`diff.<n>.*`) を覆えていなかった。

この経路は **v0.37.0 に rebase 経由で出荷されていた**。config を走査して無効化する修正を
施した (`crates/kagi-git/src/cli.rs`、ADR-0146 系)。

**F-01 と F-02 の対比が RQ1 の答えである。** 「CLI のほうが安全」という当初仮説は成立しない。

### 3.2 index stat cache — 遅延の主因

**F-03 — libgit2 は refresh した index stat cache を書き戻さないため、陳腐化した
repository では毎回全内容を再ハッシュし続ける。**
確信度: 高 (機序を特定し、修正して実機で検証)。

libgit2 は index の stat data と一致しない file の内容を毎回ハッシュし直す。`git status` と
異なり refresh を書き戻さないため、この費用は scan のたびに永久に発生する。内容を変えずに
file を触る操作 — build、同一 bytes を書き直す formatter、copy からの復元 — がこの状態を
作る。

**表 1** 50,000 file、同一 repository、libgit2 の full status

| 状態 | 所要 |
| --- | ---: |
| warm index | 135 ms |
| 全 file を `touch` した直後 | 3,305 ms |
| その次の scan | 3,318 ms |
| 端末で `git status` を 1 回実行した後 | 143 ms |

自己修復しない。端末の `git status` は自身を速くするだけでなく、後続の libgit2 も速くする。

**F-04 — 修正により実機の初回 load が 4.25 秒から 0.09 秒になった。**
確信度: 中 (n=1 の end-to-end 確認。統計値ではない)。

条件: `/tmp/kagi-627-p4/L` の新規 copy (tracked 50,000、286 MB)、`chmod -R u+w` 後に
全 worktree file の stat のみを変更 (内容不変)、実機 Kagi の初回 load 前後で `.git/index`
の mtime と `git status --porcelain` の実時間を 1 回測定。

修正は `GIT_STATUS_OPT_UPDATE_INDEX` の限定的な適用 (ADR-0193)。詳細は §7.3。

### 3.3 性能

**F-05 — 単体 `status` は 5,000–20,000 file の間で優位が入れ替わる。**
確信度: 高 (両順序、30 measured、$R^2$ 併記)。

**表 2** A3 正規化 scale series (`libgit2 → CLI / CLI → libgit2` の median ms)

| files | libgit2 | CLI | CLI / libgit2 |
| ---: | --- | --- | ---: |
| 1,000 | 22.858 / 21.122 | 30.968 / 31.215 | 1.35–1.48 |
| 5,000 | 33.807 / 31.557 | 37.349 / 37.787 | 1.11–1.20 |
| 20,000 | 77.523 / 68.150 | 61.176 / 58.336 | 0.79–0.86 |
| 50,000 | 152.776 / 209.579 | 95.228 / 107.250 | 0.51–0.62 |

順序別 OLS (1k 単位) は libgit2 `2.651–3.875 ms/1k` ($R^2 = 0.980$–$0.999$)、
CLI `1.304–1.547 ms/1k` ($R^2 = 0.993$–$0.999$)。傾き比 `2.03–2.51×`。

P0 の `prepare_series` で prime した formal series でも同じ向きである
(libgit2 `2.246 / 2.200 ms/1k`、CLI `0.875 / 1.101 ms/1k`)。ただし CLI の一方の順序は
$R^2 = 0.757$ と低く、小規模では順序感度が大きい。

**F-06 — composite の `snapshot` は全規模で libgit2 が速い。**
確信度: 高 (両順序、30 measured、PM が独立再現)。

**表 3** A2 `snapshot` (median ms)

| fixture | libgit2 | CLI | CLI 最重段 |
| --- | --- | --- | --- |
| S / 200 | 2.951 / 2.894 | 119.862 / 120.500 | `status` (13.630 / 13.677) |
| M / 1,194 | 19.065 / 24.926 | 142.311 / 140.867 | `commits` (25.514 / 25.525) |
| L / 50,000 | 200.777 / 173.259 | 344.556 / 242.053 | `status` (177.334 / 120.859) |

CLI 合成は 9 プロセスを起動する。libgit2 は 0 である。独立再現 (S、12 反復から warm-up 2 件
除外) では libgit2 median 2.492 ms / procs 0、CLI median 134.854 ms / procs 9 を得た。

**F-05 と F-06 は矛盾しない。** 単体 status では走査費用が支配し、composite では
プロセス起動が支配する。**単体の crossover は composite の既定を覆さない。**

**F-07 — CLI 合成は情報等価でない。**
確信度: 高。

CLI 合成は libgit2 の `snapshot()` が返す次の 4 項目を返さない。

1. linked-worktree common-dir の `FETCH_HEAD` mtime
2. 10,000 commit budget の外にある detached worktree root
3. annotated tag の target peeling
4. linked worktree の WIP counts

いずれも CLI の原理的限界ではなく現合成の未実装である (`rev-parse --git-common-dir` +
mtime、worktree HEAD + pinned rev-list、peeled ref atom、各 worktree の parsed status で
実装可能)。ただし追加プロセスと複雑性を伴う。

A2 の判断基準は「合計が libgit2 の 0.7 倍以下**かつ情報等価**」であったため、
**全置換の条件は時間を測る前から満たされない。**

**F-08 — untracked cache の有無は判定材料にならない。**
確信度: 中 (単一 host、順序差を越えない)。

L に tracked modification 1 件と untracked file 100 件を加えた条件で、libgit2 / CLI とも
canonical status は 101 entry で完全一致した。cache on は CLI を `4.3% / 1.5%`、libgit2 を
`7.7% / -1.1%` 動かしたが、順序差と single-host tail を越える一貫性はない。

**F-09 — fsmonitor は libgit2 に効果がない。**
確信度: 高。

libgit2 は built-in fsmonitor を利用しない。CLI candidate は fingerprint を変更した。

### 3.4 意味論と混在

**F-10 — stash family の混在経路で、探索した範囲では plan 予測と実行後状態の食い違いは
生じなかった。**
確信度: 低 (探索範囲が狭い)。

CLI が作成した stash に libgit2 の `Backend::plan` / `run_recorded` を適用する経路で、
S fixture (200 files)、3 candidate × 3 反復を実施した。`f-apply` / `f-pop` / `f-drop` は
いずれも `verified=true`、blockers 空、error なしであった。

**これは「混在が安全」の証明ではない。** 未実施の範囲を §6.2 に挙げる。

**F-11 — B2–B7 の意味論 (autocrlf、ignore、submodule、sparse checkout、partial clone、
unrelated histories) は未測定である。**
確信度: — (測定なし)。

backend 間に差があるか否かは**未確定**である。submodule / sparse checkout / partial clone に
ついては、機能の有無・部分対応・黙った無視のいずれであるかも検証していない。

**F-12 — Kagi の `stash apply` は衝突を事前に予告していなかった。これは backend 間の
意味論差ではなく Kagi の実装差である。**
確信度: 高 (実測、修正済み)。

同一条件で `pop` は予告し `apply` は予告しなかった。原因は `plan_stash_apply` に
三者マージによる予測段が無かったことである。backend 選定の結論からは除外し、
製品欠陥として修正した ([#652](https://github.com/TomiXRM/kagi/issues/652))。

### 3.5 watcher

**F-13 — FS watcher の debounce により、保存の連打は status scan を積み上げない。**
確信度: 中 (単一条件、計測用出力による直接計数)。

50,000 file の repository で 60 回の保存を 50 ms 間隔で流し、single-flight を実装した build に
計数出力を入れて測定した結果、**scan 6 回 / skip 0 回**であった。CPU も 3 試行で有意差が
なかった (main `2.32–2.55 s` 対 実装版 `2.56–2.64 s`)。

含意: 「重複排除の仕組みが無い」という構造の事実から「重複が起きている」を推論しては
ならない。単一 flight 化は実装したが**効果がないため破棄した** (§5.3)。

## 4. 局所最適化

**F-14 — pathspec を指定した status は、同一 backend 内で桁違いに速い。**
確信度: 中 (owner 測定、n が小さい)。

同一 L fixture (tracked 50,000) の libgit2 measurement:

**表 4**

| index 状態 | full status | pathspec status |
| --- | ---: | ---: |
| stale | 5,427 ms | 0.8 ms |
| **warm** | **145.3 ms** | **1.2 ms** |

**比較は warm 同士 (約 121×) のみを用いること。** stale の full と warm の pathspec を
対比してはならない (§5.2)。

これは意味論を変えない局所最適化であり、backend 選択とは独立に効く。適用には
rename / ignore / directory 無効化のための full-scan fallback が要る。

## 5. 測定手法上の落とし穴 (否定的結果)

本節は再測定と誤読を防ぐために残す。#627 では**同種の誤りが三度**発生した。

### 5.1 fixture copy による index stat cache の陳腐化

P0 の pristine copy は index の stat data と file の inode / ctime を不一致にする。この状態で
測ると **backend の性質ではなく陳腐化した index を測る**ことになる。CLI は初回に index を
自己修復するため、この交絡は「CLI のほうが速い」という誤った結論を生む。

50k で libgit2 が CLI の約 3 倍遅いという初期の観測は、この交絡であった。20k でも同様
(libgit2 `1,179.8 → 77.5 ms`、CLI `423.8 → 61.2 ms`)。**当初「信頼できる」と判断していた
20k 以下の傾きも汚染されていた。**

対策は §2.3 の正規化手順である。

### 5.2 測定条件を切り離した数値の引用

三度の誤りはいずれも「値を測定条件から切り離して読んだ」ことに起因する。

1. fsmonitor 実験の 20k における native Git の値 `9.739 ms` を、50k の CLI 値と取り違えた。
   これを根拠に 50k 実測値の全体撤回を指示しかけた。
2. stale index で測った `5,427 ms` を warm の pathspec `1.2 ms` と対比し、pathspec の効果を
   約 37 倍過大に見せた (§4 で訂正)。
3. refresh の頻度から scan の頻度を推定し、実測せずに最適化を優先度付けした (§5.3)。

**対策として、canonical output に測定条件そのものを持たせる**運用を採った
(`wall_ns_includes_setup`、`index_warm_at_series_start`、`index_mtime_changed`)。
report の本文だけに条件を書いても、JSON を読む者には届かない。

### 5.3 構造の事実から挙動を推論した誤り

「同一 revision の status 読み取りに重複排除が無い」は構造の事実である。そこから
「重複が起きている」を推論して single-flight を実装したが、実測では重複が起きていなかった
(F-13)。実装は破棄した。

### 5.4 その他

- 計測は broken build で行われうる。probe が compile しない状態の測定値が一度報告された。
- probe が backend を分岐していないのに「比較」として報告されうる。一方の probe が
  `context.backend()` を参照しておらず、両 backend で同一経路を実行していた事例がある。
- 用意した fixture への書き込みが permission により失敗し、変異させたつもりの検証が
  何も検証していないことがある。

## 6. 妥当性への脅威

### 6.1 外的妥当性

- **単一 host (macOS arm64) の測定である。** Linux / Windows の headless probe と native GUI
  evidence は未取得。CLI mode の既定昇格・OS 別規則・新 backend 採用はいずれも**未確定**。
- fixture は synthetic generator が主であり、実 repository の分布 (深いディレクトリ、
  巨大な単一 file、多数の submodule) を代表しない。

### 6.2 内的妥当性

- **F-10 の探索範囲が狭い。** 未実施: apply が競合する同一 path の別内容、S より大きい
  fixture、untracked を含む復元の境界。
- **P5 D2 (syscall 回数 / read bytes) は未測定。** macOS の `fs_usage` が root 権限を要求した。
  「なぜ遅いか」の機序診断が欠けている。
- **libgit2 の段別内訳が無い。** production の `snapshot()` に stage 単位の計測 seam が無いため、
  最も重い libgit2 の段は `working_tree_status` 以外分かっていない。F-06 の局所候補
  (`status`) を他段へ一般化してはならない。
- **F-04 は n=1** の end-to-end 確認であり、統計値ではない。
- B2–B7 未測定 (F-11)。

### 6.3 構成概念妥当性

- CLI は Kagi の oplog を作らないため、recovery handle 軸は **比較不能**である。state
  transition が一致しても recovery の同値を導いてはならない。

## 7. 決定

正式な決定は [ADR-0194](../../adr/0194-git-backend-selection.md) にある。要点のみ再掲する。

### 7.1 既定は libgit2

主根拠は F-01 の安全性であり、速度ではない。F-06 が速度面でも支持する。

### 7.2 CLI は明示 mode のみ、自動切替は採らない

F-05 の crossover は事実として保持するが、規模による暗黙の切替は採らない。Kagi は実行前の
予測を提示する製品であり、**予測経路の挙動が入力サイズで暗黙に変われば製品の前提が壊れる**。
F-11 が示すとおり backend 間の意味論差は大半が未測定であり、それらが repository の成長に
伴って無言で発現することになる。

### 7.3 局所最適化は backend 選択から分離する

index stat cache の repair (F-03、F-04) と pathspec status (F-14) は意味論を変えない局所
最適化であり、既定 backend を変える根拠にしない。repair は read/write 契約を満たす形に
限定した (ADR-0193): 既定の読み取りは純粋な read のまま、UI の refresh 経路のみが opt-in
する。`plan_*` / `preflight_*` は confirm 前に走るため書き込んではならない。

### 7.4 不変条件

**全 write の `plan → confirm → preflight → execute → verify → oplog` は backend 選択と
無関係に不変である。** F-10 の 0 件はこれを緩める根拠にならない。

## 8. 今後の課題

優先度順。詳細は §6 を参照。

1. **Linux / Windows の証拠取得** (§6.1)。採用 gate が 3 OS を要求しており、現在の決定は
   単一 host に立脚している。`.github/workflows/backend-probe.yml` (`workflow_dispatch`) が
   3 OS で `backend_probe` を実行し、`uv run --project ci probe-report` が結果を要約する。
   **runner の hardware が異なるため OS 間の絶対値は比較できない。** 移植可能なのは
   (a) 同一 runner 内で両 backend の canonical 出力が一致するか、(b) 同一 runner 内の
   比 CLI/libgit2 の 2 つだけであり、report tool はこれを強制する。
2. **B2–B7 の意味論測定** (F-11)。とくに submodule / sparse checkout / partial clone は
   「黙って無視される」場合が最も危険であり、予測の正しさに直結する。
3. **production `snapshot()` の stage 計測 seam** (§6.2)。private helper を露出させずに
   段別の時間を得る設計。F-06 の局所候補を一般化する前提。
4. **F-10 の境界条件** (§6.2)。競合する apply、大きい fixture、untracked 復元。
   [#652](https://github.com/TomiXRM/kagi/issues/652) の修正により apply の予測が入ったため、
   予測の正しさを試す条件が整った。
5. **D2 の代替診断** (§6.2)。root 権限を要さない syscall / bytes の観測方法。
6. **pathspec status の設計** (F-14)。full-scan fallback の無効化条件 (rename、ignore、
   directory) を定義できるか。#657 により緊急性は下がっている。
